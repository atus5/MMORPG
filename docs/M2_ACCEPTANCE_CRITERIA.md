## I — identity and ownership

- **I-01:** With two explicit local test principal contexts, each can select/control only owned characters through Account → Player → Character. Invalid, expired, missing or revoked context, disabled account and wrong ownership are denied before protected state. Account ID, Player ID and Character ID are distinct and cannot be confused with session/connection IDs. Real JWT/provider verification is NOT_IMPLEMENTED in M2 and cannot be claimed tested using fakes.
- **I-02:** Missing/unapproved Origin is rejected independently of token checks. Origin spoofing by a non-browser does not bypass verified identity/ownership.
- **I-03:** Ticket replay, expiry, origin/character mismatch, Redis replay after restore and concurrent redemption across gateways cannot create two control grants. PostgreSQL unique redemption is tested, not inferred from Redis GETDEL.
- **I-04:** Same character cannot accept input from two bindings. Approved conflict/takeover behavior and revocation bounds are demonstrated. An account can own multiple characters; no hardcoded quota or unique-character-per-account constraint. Creation with missing policy returns `POLICY_NOT_READY`; approved quota/name rules are configuration inputs, not arbitrary defaults.
- **I-05:** NR-M2-002: only trusted server composition at startup selects the local/test adapter. Header/query/cookie/message/handle/provider-failure attempts cannot switch it or activate test mode; production has no fake fallback. Server-side principal fixtures and opaque browser handles, if approved, are isolated by run and lifecycle; forged/cross-run/expired/revoked handles fail. Fixture/persistence target approval remains required; in-memory success is not real Auth or PostgreSQL coverage.
- **I-06:** NR-M2-006: change account status, ownership, principal validity/revocation version, membership/placement or current control after ticket issue and before redemption/lock acquisition. Under the declared locks, stale authorization/binding is denied; grant/result/redemption commit together exactly once. Missing revocation/freshness policy fails closed. Provider/Redis calls occur outside the transaction and cannot replace post-lock local checks.
- **I-07:** Race two gateways redeeming the same ticket; inject commit-ack loss and delayed completion. No welcome/second grant occurs while the first outcome is uncertain. Resolve by the same durable operation/redemption identity; an empty lookup while a transaction remains in flight is not proof of abort. Returning a committed result requires current authorization, matching digest and no replay of an obsolete binding.

## W — worlds, spawning and data boundaries

- **W-01:** Two clients in the same approved world/area observe the same public entities and authoritative movement. Different-world clients receive no unauthorized world/entity/private account data.
- **W-02:** Nhân Giới, Linh Giới and Tiên Giới have distinct stable world identities and configured map revisions. More gateways/processes do not create personal/shadow copies of a logical world.
- **W-03:** Server randomness chooses only valid approved spawn geometry. Test empty/invalid geometry, blocked candidates, sampling-attempt exhaustion and absent policy; no unbounded loop or coordinate/world fallback.
- **W-04:** Concurrent/retried spawn requests produce one committed result. Crash after database commit and before welcome recovers the same spawn. Reconnect does not reroll. Map-revision mismatch requires an explicit approved recovery policy.
- **W-05:** Starting world/eligibility/transitions and any separation/collision/safety constraints are Owner-approved test inputs. No automatic realm progression or protection rule is introduced.
- **W-06:** World Membership is durable placement, independent of Redis presence/session. At most one active membership per character. World Transition is a separate policy/orchestration interface; absent policy denies transfer. No free travel, reverse travel, point reset/loss or count limit is inferred. Confirmed thresholds 1000000 and 10000000 are preserved, not used as a complete transition policy.
- **W-07:** [Confirmed reference](GAME_RULES_REFERENCE.md) retains every supplied realm value, three sub-realm names, outfits and Đạo Tổ facts. Luyện Hư/sub-realm numeric thresholds remain absent. No progression/combat implementation or unrestricted cross-world data exposure is added.
- **W-08:** NR-M2-003: Character/Player IDs are distinct from canonical membership identity/version. Even with absent child rows, Account/Player/Character anchors serialize first spawn. Concurrent same-key/same-request and different-key requests commit at most one active membership with matching checkpoint/grant/result/outbox and admission redemption where applicable. Recheck authorization, policy/geometry/candidate/current fence after locks; crash/uncertain commit returns the known result without reroll. Approved dynamic occupancy predicates require tested serialization. Missing starting world/realm/fixture geometry denies affected spawn.

## T — authoritative movement and F-002

- **T-01:** An integration-only arithmetic fixture defines `[0,0.05)`, right admitted at `0.01` and idle at `0.04`, and displacement `V × 0.03` before publication on an unobstructed one-dimensional map. `V` is a fixture input, not a gameplay default. This checks the integrator only; manually supplied admission timestamps cannot establish receiving-path correctness or close F-002 without T-11/T-12.
- **T-02:** Test multiple direction changes in one tick, equal-time transitions ordered by sequence, an event at a tick boundary, zero elapsed time and input-lease expiry inside an interval. Results match the piecewise integral and legal map bounds.
- **T-03:** Replayed/out-of-order/duplicate sequences, future/backdated client timestamps, client delta/speed/position injection and input spam cannot grant extra authoritative distance or extend intent expiry. Only serialized owner admission time places an event on the integration timeline; socket/gateway timestamps are diagnostic.
- **T-04:** The same admitted owner timeline produces equivalent movement under different browser FPS, publication rates and bounded integration scheduling. Changed network/validation delay may change admission time and thus the authoritative trace; compare against that trace rather than claiming delivery-independent distance. No historical movement credit is granted.
- **T-05:** Delayed ticks perform bounded catch-up. Excess backlog, queue overflow, long process pause or authority expiry never becomes one oversized delta/teleport. Freeze/resync behavior and error codes are tested; stop events are not silently discarded.
- **T-06:** Received ACK, applied ACK and durable checkpoint version reflect their actual boundaries. No applied/durable claim precedes the corresponding integration/commit.
- **T-07:** NR-M2-001: distinguish `t_received`, `t_admitted` and integration time; race serialized bounded admission with `[a,b)` closure. Receipt before closure but admission afterward cannot reopen the interval; an event at `b` affects the next positive-duration segment and equal-time events use sequence order. No admission ACK precedes capacity reservation; late-input alternatives require approved policy. Ambiguous/lost timeline freezes and resyncs without backfill.
- **T-08:** NR-M2-004: obstacle/contact/turn/reversal fixtures preserve every ordered temporal segment, applying approved collision/bounds before the next segment. Include a case where summed displacement followed by collision gives a different result. Do not select hitbox/sliding/bounce/diagonal mechanics through test defaults; PO-04/05 supply them.
- **T-09:** NR-M2-007: test same-intent renewal before, exactly at and after expiry; explicit idle/release, direction change, stale intent/control generation and replayed sequence. Ping/pong cannot renew movement. A valid pre-expiry renewal extends only from its admission, cannot overwrite earlier timeline segments, and an expired renewal cannot revive motion or fill an idle gap.
- **T-10:** A physically held key after expiry resumes only through the explicitly approved fresh-input policy. Release/repress versus fresh-sample behavior remains PO-05 pending, with no implicit choice. Recovery invalidates prior queued samples/renewals and requires a fresh authorized baseline; no automatic replay/resumption.
- **T-11:** R1-001 real-path specification: use an approved isolated fixture with controlled server monotonic time and independently scheduled tick/publication loops. Submit complete right/idle frames at `0.01`/`0.04` through the production-equivalent receive/decode/validation/route/owner-ingress/admission path; the implementation generates both `t_received` and `t_admitted`. Do not inject admission timestamps, call only admission/integration directly or prefill an already-admitted queue. In the no-injected-delay case, observe both admissions before closure at `0.05`, in sequence with a positive right segment; assert displacement `V × (t_idle_admitted - t_right_admitted)` and approximately `V × 0.03` within an explicitly approved tolerance derived from measured admission latency. Require the approved latency budget, not just nonzero distance. A mailbox drained only at tick end must fail even if T-01 passes. `V`, geometry, intent expiry, scheduler resolution and tolerance are declared fixture inputs; missing approval cannot pass this gate.
- **T-12:** R1-001 delay/metrics specification: inject delay after owner observation but before actual admission, with the tick loop still independently scheduled. Verify same-clock `input_admission_latency_seconds`, sample count/histogram/p50/p95/p99/max, pending depth/oldest age and budget-exceeded/reject/freeze counters include the observed behavior. An event exceeding approved `T_admission_budget` freezes/resyncs the binding without backdating or admitting stale right/idle together as successful motion; pending ingress is bounded even if admission never completes. Separately pause the loop before observation: distinguish event-loop lag from receipt-to-admission latency and claim no reconstruction of unobserved press time. PO-07/08 must supply budgets/metric settings and PO-05 supplies late-input/held-key policy; no numeric threshold is introduced. These are future specifications, NOT_RUN.

## S — real-time synchronization

- **S-01:** Initial join and reconnect receive a full authorized AOI baseline. Enter/state/leave, world/map IDs, owner epoch, stream ordering and entity versions are validated in both browser and backend.
- **S-02:** Missing Pub/Sub messages, new subscriptions, baseline mismatch and old-owner publications cause bounded full resynchronization. No delta is applied to an unknown baseline.
- **S-03:** Bounded slow-client queues preserve lifecycle/control semantics or explicitly force resync/disconnect. Output coalescing does not coalesce the owner's inbound input transitions.
- **S-04:** Repeated connect/loss/recovery/reload does not duplicate characters, canvases, handlers, timers or manager entries. Old epochs/input buffers cannot affect the recovered session; existing M1 cleanup regressions still pass.

## P — durability and authority safety

- **P-01:** Account/player/character/membership/position/map FK/version constraints and any approved configurable per-account limits are verified under concurrency in an approved local/non-production PostgreSQL target. No production migration or real Auth service is needed or authorized by this test criterion.
- **P-02:** Race a checkpoint writer against owner takeover and control-generation replacement. Transactions lock/validate lease/grant rows and CAS position versions in the declared order; old writers never commit through a check/use race.
- **P-03:** Pause the old owner beyond lease expiry; acquire a newer owner; resume the old process. Old inputs, publications and checkpoint writes are rejected. Redis expiry or a routing hint alone cannot acquire authority.
- **P-04:** Crash at each spawn/grant/checkpoint/outbox boundary. Recovery meets the approved checkpoint RPO/RTO and idempotency contract. State ACK does not promise durability; zero-loss claims require a separately reviewed durable-log design.
- **P-05:** Test actual connection-pool mode, transaction scope and timeout behavior. RLS/auth context cannot leak across pooled requests; session-level assumptions are not used to protect writes.
- **P-06:** Duplicate metadata delivery is harmless, event IDs/aggregate versions are checked, and relay restart can replay from durable outbox state. No exactly-once delivery claim without an end-to-end proof.
- **P-07:** NR-M2-005: validate ADR-0004's operation matrix against actual schema/FK/index/trigger/isolation locks. Race first spawn, redemption, account/ownership changes, control replacement, overlapping checkpoint batches and reversed source/target transitions. All keys are acquired rank by rank with strongest mode first; discovered earlier resources cause abort/restart. No missing-child-row lock assumption, lock upgrade or operation-key-first inversion bypasses anchors. Record actual deadlocks/retries honestly; proposed reasoning alone is not a concurrency PASS.
- **P-08:** Race bounded checkpoint batches with lease-only renewal/takeover. Shared lease readers block lease updates but no lease-only updater waits on a Character/grant lock, eliminating the declared reverse edge. Test renewal delay, lock/statement/transaction timeout, advancing database-time expiry and uncertain renewal commit. No expired owner extends its safe deadline on assumed success. Batch size, wait, renewal margin and RPO/RTO limits require approval/measurement; no Redis/external RPC or retry sleep occurs under transaction locks.
- **P-09:** R1-002 specification for the approved physical persistence design: attempt checkpoint/grant writes with mismatched character, membership identity/version, world, map revision or partition, including a stale projection racing an approved membership change. Reject mismatches against the canonical membership tuple under the declared locks/approved constraints; matching projections remain valid. ER fields are conceptual projections, not independent placement assignments or proof of a composite FK. Record how the separately approved join/projection or retained-column constraint/transaction design enforces the invariant. No DDL/schema change or database execution is performed by this documentation criterion.

## R — Redis and failure handling

- **R-01:** Delayed cleanup with an old generation cannot delete current presence or membership. Stale-index pruning and presence renewal are atomic within the configured hash slot.
- **R-02:** Expire/delete/restart Redis data: durable characters/positions remain; online status becomes unknown or rebuildable; new tickets fail closed while unavailable. No second owner appears.
- **R-03:** Kill Pub/Sub subscribers and inject publication gaps: gateways resync. Redis Stream/outbox consumer retries/duplicates/retention are tested if that adapter is in the approved scope.
- **R-04:** Database outage, failed checkpoint/lease renewal, Redis outage, owner death and gateway death follow the documented failure behavior. Recovery requires fresh verified authority; no fallback trusts client state or stale Redis coordinates.

## Q — security, capacity and final acceptance

- **Q-01:** No secrets/private env/auth cache/service-role key in browser bundles, repository, messages or logs. Validate sanitized errors, per-IP/account/character admission budgets, size/rate/queue caps and authentication deadlines.
- **Q-02:** Run the approved workload: CCU per world/partition, AOI density, traffic/burst/lag/disconnect patterns and duration. Record p50/p95 tick time, input age, event-loop lag, receive-to-admission latency count/histogram/p50/p95/p99/max, pending admission age/depth, budget-exceeded/reject/freeze counters, memory, egress, checkpoint latency and recovery times. Thresholds/metric settings must be approved before testing; placeholder numbers cannot pass a performance gate.
- **Q-03:** A multi-process integration run uses at least two gateways with one authoritative owner for a shared partition, and demonstrates no duplicate authority when scaling. A hotspot's single-owner limit is reported honestly.
- **Q-04:** Execute the complete relevant frontend/backend/protocol/database/Redis/browser/failure suites; preserve real outputs and NOT_RUN items. Developer review, exact Git scope, secret checks and remote SHA verification accompany meaningful commits.
- **Q-05:** Seal a new full-content snapshot and obtain independent Gemini milestone review before proceeding. Neither AI merges main or deploys. Production schema work remains separately authorized.
